# MuJoCo 车载相机与地面变化诊断

本页路径相对于仓库根目录。命令示例从仓库根目录的 CMD 开始；第一次 cd 进入本阶段目录。依赖安装见[仓库说明](../README.md)。

这个版本让机器人在 MuJoCo 中真正运行，并从车载前下视相机生成 RGB 图像。它分别检查两件事：相机是否看到地面外观变化，以及实际运动是否出现异常。两类线索一起显示，但地面的外观不会直接等同于摩擦系数。

本版的控制器继续使用动力学自适应。视觉只提供诊断，不根据识别结果提前减速或切换估计窗口，因此不能把视觉提示本身当作轨迹跟踪已经改善的证据。

## 第一次运行

1. 打开 `mujoco_vision_ready`。
2. 双击 `start_vision.cmd`。
3. 查看实时三维场景、程序提供的相机画面和终端提示。
4. 实验结束后，打开终端打印的结果目录，查看相机图像、识别记录和诊断图。

默认场景是 `visible_low_friction`：地面外观与实际接触摩擦都会变化。实验运行 18 秒，控制频率 50 Hz，相机识别和诊断报告频率 5 Hz；模拟路面在世界坐标 `x = 4` 米处分界，低摩擦场景的接触摩擦系数由 0.8 变为 0.02。电机故障场景在第 8 秒把左电机效率降为 0.5。

项目预装 `prepared_model`，无需重新训练即可运行。关闭任意实时窗口会提前结束，保存已运行数据，并标记 `complete=false`；这种部分结果不能当作完整 18 秒实验比较。

实时窗口和相机渲染会占用计算资源，完成 18 秒模拟可能需要超过 18 秒实际时间。图像处理运行在每个相机采样时刻；这里没有测定实际机器人的实时计算能力。

启动器优先使用上一级目录的 `.venv\Scripts\python.exe`，找不到时调用命令行中的 `python`。所需的 MuJoCo、NumPy、Matplotlib 和 Pillow 已列在 `requirements.txt`；启动器不会自行安装软件或改动系统设置。

## 命令行操作

在已经激活原虚拟环境的 CMD 中运行：

```cmd
cd /d mujoco_vision_ready
python run_vision.py
```

执行全部对照场景：

```cmd
python run_vision.py --all-cases --headless
```

也可以双击 `run_vision_checks.cmd`。`--headless` 不打开交互式三维窗口；实验仍需要渲染相机图像，并非完全跳过图形渲染。

单独选择场景：

```cmd
python run_vision.py --case visible_surface_only
python run_vision.py --case hidden_low_friction --headless
python run_vision.py --case motor_fault --seed 3
```

| 参数 | 含义 |
|---|---|
| `--headless` | 不打开交互式三维窗口，继续生成相机图像与结果 |
| `--all-cases` | 依次执行全部五个对照场景 |
| `--case normal` | 正常地面与正常驱动 |
| `--case visible_surface_only` | 外观变化，接触摩擦不变 |
| `--case hidden_low_friction` | 接触摩擦降低，外观不变 |
| `--case visible_low_friction` | 外观与接触摩擦同时变化 |
| `--case motor_fault` | 电机输出异常，地面外观不变 |
| `--seed 3` | 指定实验随机种子 |
| `--output-dir results_test` | 指定结果保存目录 |
| `--retrain` | 重新生成训练数据、训练分类器并执行保留集测试 |

## 相机实际识别什么

小型外观分类器只识别三种模拟纹理：

| 标签 | 含义 |
|---|---|
| `tile_grid` | 砖块网格状外观 |
| `speckled` | 颗粒状外观 |
| `parallel_stripes` | 平行条纹状外观 |

这些是图像外观标签，不是对真实瓷砖、砂石、金属或湿滑材质的语义识别。离线训练使用已知纹理标签；运行时分类器的输入只有 RGB 像素，不读取地面编号、真实摩擦系数或机器人位置。训练与测试按整套纹理随机种子、光照和相机视角区分，不把同一段视频的相邻帧随机拆分来充当泛化测试。

当前训练集包含 60 张真实 MuJoCo 渲染的 RGB 图像，每类 20 张，使用不同纹理种子。未见纹理种子的测试集另有 30 张，其中 29 张识别正确、1 张被拒识为 `unknown`，没有误判为另一个已知类别。这只说明当前模拟纹理集合的结果。运行时还使用与训练、测试分开的纹理种子 1000、1001。

程序对 `appearance.py`、`surfaces.py`、`engine.py`、`robot.xml` 以及模型和数据集进行哈希校验。修改相机、特征或相关场景生成代码后，需运行 `python run_vision.py --retrain`，重新生成数据和模型，避免继续使用不匹配的缓存。

场景中的地面由有限尺寸的接触盒组成，轮地摩擦通过显式接触对设置。纹理和接触摩擦独立配置，既能出现不同外观但相同摩擦，也能出现相同外观但不同摩擦。旧实验用来审计故障的轮胎变色已禁用，参考标记也不进入识别用 RGB 图像，避免分类器利用这些提示。

## 如何解释诊断

| 观察到的线索 | 合理结论 |
|---|---|
| 前方纹理变化 | 前方外观发生变化，物理影响等待确认 |
| 运动预测残差持续增大 | 当前动力学出现异常，原因尚未确认 |
| 带噪轮速与车体速度出现明显差异 | 可能存在滑移，可作为辅助线索 |
| 外观变化同时伴随运动异常 | 路面变化与异常同时出现，提供相关线索，不能直接作因果确诊 |
| 地面图像不变但运动异常 | 可能有不可见路况或驱动故障，需要其他传感器进一步区分 |

单凭地面图像不能确认电机故障；通常还需电流、电压、编码器等信号。轮速与车体速度差也不是完整故障诊断。视觉不能唯一确定摩擦系数，湿或暗的地面不一定更滑，纹理明显变化也不代表机器人一定受到影响。

对照实验用于检查这些边界：只换外观时不应直接报告摩擦降低；隐藏低摩擦时不能依赖图像发现变化；电机故障时不能把动力学异常自动解释为地面变化。低摩擦是否造成明显运动异常，还取决于速度、转弯、扭矩和抓地需求，应结合实际日志判断。

外观变化标志在首次出现后锁存，因此它可能与较晚出现的当前运动异常同时为真。本版没有把两者做空间对应，这种同时出现不能说明来自同一段地面或同一个原因。

## 输出文件

每次场景运行保存 `robot_log.npz`、`camera_predictions.csv`、`camera/*.png` 和该次的 `vision_report.json`。输出根目录保存 `vision_dashboard.png`、汇总 `vision_report.json`、`config_used.json`、`calibration.json`。项目中的 `prepared_model` 包含 `model.npz`、`appearance_dataset.npz` 和 `heldout_test.json`。具体结果目录以终端输出为准。

先看总览图中外观识别、运动残差与诊断时间线的关系，再查看对应的原始相机帧。保留 CSV 和日志，确认提示发生在观测之后，而不是因为程序提前知道场景变化。分类器的保留集成绩只说明这些模拟纹理、光照和视角条件下的识别表现，不代表真实室外识别性能。

## 已完成的对照检查

运行种子 0、1 各执行了全部五组配对场景，均已完成。当前配置下观察到：

| 场景 | 首次诊断报告 |
|---|---|
| 只换外观 | 约 5.22 秒报告视觉变化，没有运动异常或滑移报警 |
| 隐藏低摩擦 | 没有视觉变化报告，运动异常和滑移线索可以出现 |
| 外观与低摩擦同时变化 | 视觉约 5.22 秒、滑移约 5.82 秒、运动异常约 6.22 或 6.42 秒 |
| 电机故障 | 第 8 秒故障后，仅运动异常约 8.22 或 8.42 秒报告，根因保持未知 |

路面接触变化在该配置中约为 5.46 秒；上述诊断时间是 5 Hz 报告的首次出现时间，不是精确到 50 Hz 控制步的触发时刻，也不表示视觉在一般条件下都能提前 0.24 秒。低摩擦场景轨迹误差仍然较大；视觉未改变控制，不能据此声称已经改善移动控制。

## 目前的范围

本版实现模拟相机外观识别与运动异常线索的解释性融合，没有实现神经潜在状态模型，也没有训练真实材料语义识别网络。若要识别真实道路、草地、砂石或湿地，需要先采集真实相机图像并标注，再训练和验证分类或分割模型。仅靠本次模拟不能声称已具备真实室外地面识别能力。

本项目在轮轴关节增加了系数为 0.01 的线性阻尼，避免理想恒定扭矩在极低摩擦时无限空转；它不是按实际电机标定的驱动模型。

运行失败时，保留终端中的完整报错，确认使用的是原项目虚拟环境。相机渲染需要可用的图形环境，即使选择 `--headless` 也应检查 MuJoCo 的离屏渲染是否可用。
